# Plan: Leaderboard silent-submit-failure fix + invite/share flow repair
_Locked via grill — by Claude + kiddulu916_

## Goal
Two independent fixes in the app-side (Flutter/Supabase) codebase, scoped after live investigation ruled out the originally-reported symptom (the leaderboard is showing scores again post-wipe) and instead confirmed three concrete, still-live defects: (1) `GameCubit._submit()` can permanently block retry of a failed score submission because its idempotency guard is set before the submission's real server-side outcome is known — including cases that don't throw at all; (2) the Facebook/OS-share-sheet path in the score-share flow sends the invite link/code as pixels baked into an image only, never as accompanying text, so the actual link is not shareable/tappable; (3) the friend-referral auto-link-on-install flow cannot work for any real-world Play Store install because no invite link this app generates carries the Play Install Referrer `&referrer=code=<code>` parameter Google needs to hand back to a fresh install, and separately, the redemption coordinator currently requires a linked Google identity before it will apply an install-referrer-sourced code, which blocks guest-only installs. Acceptance for "the invite link opens the app" is scoped to **Android** — the confirmed-broken, tested platform; iOS's equivalent (Universal Links) needs a same-repo Associated Domains entitlement this plan does not add (see Out of scope). A fourth, related requirement — hosting `assetlinks.json`/`apple-app-site-association` and adding the Play Store referrer redirect on `www.connectmerge.app` — lives in a separate repo (`connectmerge-site`) and is explicitly out of scope here; this plan documents the exact spec that repo's own session needs.

## Approach

### Track A — Score-submission silent-failure fix
1. **Stop discarding the server's verdict, without coupling the application layer to infrastructure.** Define a small, app-owned `SubmitOutcome` (e.g. `enum SubmitOutcome { success, retryableFailure, terminalRejection }`) alongside `GameCubit`; change `SubmitRun` (`lib/application/game_cubit.dart:63`, currently `Future<void> Function(...)`) to return `Future<SubmitOutcome>`. `GameSessionFactory._submitRun` (`lib/application/game_session_factory.dart:58-68`) — already the designated infra/application bridge per its own docstring — calls `leaderboard!.submitRun(...)`, inspects the `SubmitResult` (add a `reason` field to it, `lib/infrastructure/leaderboard_service.dart:9-27`, parsed from `j['reason']`), and maps it to `SubmitOutcome` there, so `game_cubit.dart` never imports `leaderboard_service.dart`/`supabase_flutter` and keeps its existing plugin-free callback boundary (matching `onCoinsEarned`/`onTierCompleted`). This matters because a 422 rejection does **not** throw (confirmed via the existing test `test/infrastructure/leaderboard_service_test.dart:48-61`) — a fix keyed only on "did the call throw" cannot distinguish a real rejection from a real success.
2. **Outcome branching in `_submit()`** (currently ~`game_cubit.dart:540`): call the hook and branch on the mapped outcome instead of a bare try/catch setting the guard unconditionally:
   - Thrown exception (network/transport/auth failure) → leave `_submitted == false`, retryable.
   - `SubmitOutcome.success` (server `valid == true`) → `_submitted = true`, done.
   - `SubmitOutcome.retryableFailure` — maps `reason == 'submit_failed'` (FK race — the `players` row didn't exist yet server-side) **and** any unrecognized/missing `reason` on a `valid:false` response (including the production wrapper's `{'valid': false}` fallback for a malformed response shape, `leaderboard_service.dart:49-54`) → leave `_submitted == false`, retryable, and report via `onAnalyticsEvent` so an unrecognized shape doesn't go unnoticed even though it's handled safely by default.
   - `SubmitOutcome.terminalRejection` — only `reason == 'invalid_run'` → `_submitted = true` (retrying a deterministic replay rejection can never succeed — same move log, same server-side verifier, same result every time) **but** report it via `_onError?.call(..., fatal: false)` with a distinguishing marker/message. This case existing in production would mean either tampering or — per `CLAUDE.md`'s dual-engine-invariant warning — a genuine Dart/TS engine parity bug silently eating a legitimate player's score; either way it must not vanish into the ether the way it does today.
3. **Persist a tri-state submission status as its own storage entry — not embedded in `GameSnapshot`, and defaulting missing/legacy data to `none`.** `submitIfPending()` (called on an explicit main-menu exit) has **no** terminal gate by design: a player who declines an offered ad continue and exits is intentionally finalizing a non-terminal-looking board as their real result. If that submission then fails and the app is closed, a resume that re-derives "terminal" from raw board state alone would wrongly skip retrying it (the board still nominally has an unused continue available), reintroducing the original bug for exactly this path — but a plain boolean "was it attempted" over-retries too: it can't distinguish "attempted and already succeeded/terminally rejected, don't touch again" from "attempted and still needs retry," so every resume of an already-settled completed tier would needlessly re-invoke the network call and replay verifier.
   - **Storage shape:** add `loadSubmitStatus(date, difficulty)` / `saveSubmitStatus(date, difficulty, status, generation)` to `StorageService`, following the same key-value pattern already used for `loadStats`/`saveStats` (`storage_service.dart:204-218`) — a **separate persisted entry**, not a new field on `GameSnapshot`. This matters, not just for tidiness: `GameSnapshot` is wholesale-overwritten by `saveSnapshot` calls elsewhere (`_applyUndo` at `game_cubit.dart:511`, and `grantAdReward`'s post-continue save) — if submit status lived inside the same snapshot object, a background resume-triggered retry finishing *after* the player takes an ad continue could write its `settled` status attached to the **old, pre-continue board**, clobbering the freshly-continued game's snapshot with stale data. A separate entry can't collide with the board snapshot's own writes.
   - **Generation-guarded, because a fixed `(date, difficulty)` key still isn't fine-grained enough on its own.** Taking an ad continue produces a *new* completed board (different move log, potentially a different final score) under the *same* `(date, difficulty)` — so a background retry still in flight for the *old* board can resolve and persist `settled` for that key *after* the player has already continued to a better result, permanently suppressing the improved score's own future submission. Fix: track an in-memory (and persisted) monotonic `submitGeneration` counter, bumped every time `_finishRun` reaches a new terminal state (including after a continue produces a new one). `_submit()` captures the generation it's operating on at the start of an attempt; when the hook resolves, the outcome is only applied/persisted if the captured generation still equals the current one — a stale, superseded attempt's result is simply discarded rather than written, so it can never clobber a newer attempt's status. This is the same compare-and-swap idea Codex's Round 4 finding #1 first suggested as an alternative to decoupling the storage key; both are needed together, one at the storage layer (board vs. status) and one at the logical-attempt layer (old completion vs. new completion of the same date/difficulty).
   - **Account-scoped, using the existing wipe mechanism as-is.** `HiveStorageService._installKeys` (`hive_storage_service.dart:25`) is an explicit allowlist of keys that *survive* `wipeAccountData()` (`hive_storage_service.dart:361-366`, called from `AccountFlowController._startFreshGuest`); everything else in the box is deleted on every account switch/sign-out. The new `submitStatus` key must **not** be added to `_installKeys` — it needs to be wiped on every account switch like other account-scoped data, so a fire-and-forget completion from a previous account's session can't write `settled` after switching and suppress the new account's same-day tier. Since keys are excluded from `_installKeys` by default, this is a "don't add it" correctness requirement, not new mechanism — verified with an explicit account-switch test.
   - **Values:** `none | pending | settled`. Decoded with a safe default of **`none`** for any date/difficulty with no stored value (never written yet, or written before this feature existed) — **not** `pending`. A `pending` default would force-auto-submit every legacy continue-eligible completed board the first time it's resumed post-deploy, submitting a score the player might still have intended to improve via an unused ad continue — exactly the premature-submission bug this plan is trying to avoid. The accepted tradeoff: a genuine pre-release failed-and-explicitly-finalized submission won't auto-retry on its first post-deploy resume; the player can still trigger it via `submitIfPending()` (tap Main Menu) once, same as before this fix ever existed.
   - **Ordering in `_submit()`:** check `_submitted` (see below) first and no-op if already settled; otherwise persist `pending` as the very first side-effecting step, strictly before the network call — so a process kill mid-attempt (including immediately after an offline exit) still leaves `pending` on disk for the next resume/relaunch to retry, rather than depending on the attempt finishing cleanly. Then call the hook, branch on the outcome (below), and persist the final status.
   - **Transitions:** keeps `pending` on a retryable outcome (thrown exception, or `SubmitOutcome.retryableFailure`); becomes `settled` on `SubmitOutcome.success` or `SubmitOutcome.terminalRejection` — i.e. `settled` means "no further retry needed," not "the score is definitely recorded."
   - **Seed the in-memory guard from persisted status on resume**, not just `false`: `init()`'s resume branch (`game_cubit.dart:256-262`) sets `_submitted = (loadSubmitStatus(...) == settled)` before emitting `GameOverShowScore`, so a resumed-and-already-settled run correctly no-ops if `submitIfPending()` is later called on it (e.g. an idle tap of Main Menu) instead of re-attempting a network call for an already-resolved run.
   - **Resume retry rule:** `snap.completed && status == pending` → retry (`_submit(snap.board)`) regardless of raw terminal-ness, since a prior `pending` attempt already represents either an automatic terminal-fire or an explicit player decision to finalize. `snap.completed && status == none && <terminal predicate true>` (challenge mode, deadlocked, ad-continues-exhausted, or no chain of the active minimum length available — the same predicate `_finishRun`'s caller uses at `game_cubit.dart:423-426`) → the "app died before the original auto-fire ever started" case; retry. `snap.completed && status == none && <terminal predicate false>` → never attempted, genuinely still continue-eligible and undecided; do nothing. `status == settled` → never retry.
4. **Coalesce the entire submission sequence, not just the hook call.** With the guard no longer set synchronously up front, the new resume-triggered call and an in-session `submitIfPending()` call (main-menu tap) could both pass the not-yet-settled check and both independently run the full mark-pending → call-hook → branch-on-outcome → persist-status → emit-analytics sequence concurrently — not just double-invoke the network call, but double-persist and double-report. Fix: coalesce the *entire* sequence (not only the hook invocation) behind a single in-flight `Future<void>?` on the cubit; a caller that finds one already in-flight awaits it and does nothing else itself — no redundant persistence, no redundant analytics — clearing the field once the attempt resolves.
5. **UTC-rollover retry window is honest, not silently promised as unlimited.** The server rejects any submission whose `date` isn't its own UTC-today (`submit-score/index.ts:60`, "No backfilling other days"), and the resume branch only reloads a snapshot when `snap.date == _date` (today) — a stale prior-day snapshot is simply never reloaded once the UTC date rolls over. So retry is only effective if the player reopens the app before UTC midnight after a failed submission; past that, the score is permanently unsubmittable **by server design**, not a gap this plan can or should close with more client-side persistence (a persisted cross-day outbox would just get 422'd anyway). Document this explicitly rather than implying unbounded durability.
6. **Close the same "keep best" race server-side — correctly scoped by season, locked down, and deployed in a non-breaking order.** `submit-score/index.ts:81-107` reads the existing score, decides in application code whether to upsert, then writes — not atomic. Two near-simultaneous submissions for the same `(player, date, difficulty, season)` (now more reachable than before, since this plan adds a second retry trigger) can lose the higher score to the lower one. Fix, deployed in three phases so the live `submit-score` function is never pointed at a constraint/RPC that doesn't exist yet:
   - **Phase 1 (migration):** ADD the new unique constraint on `(player_id, utc_date, difficulty, season)` **alongside** the existing `(player_id, utc_date, difficulty)` one (both can coexist — no conflict) — the current season-less constraint is a **pre-existing latent bug** this session's own research already flagged (a season bump without a full wipe would silently merge/overwrite a prior season's row). Add `upsert_best_score(p_player_id, p_utc_date, p_difficulty, p_season, p_score, p_highest_tier)`: one atomic `INSERT ... ON CONFLICT (player_id, utc_date, difficulty, season) DO UPDATE SET score = GREATEST(scores.score, excluded.score), highest_tier = CASE WHEN excluded.score > scores.score THEN excluded.highest_tier ELSE scores.highest_tier END RETURNING score, highest_tier`, with `set search_path = public` — this repo has a dedicated migration (`0005_pin_function_search_path.sql`) retrofitting every prior function that lacked this after a Supabase security-advisor finding, and every function since (`0006`, `0010`) has included it from the start; a new function skipping it would reopen the exact advisor finding that migration existed to close. Run security advisors after both migration phases. **Security contract, non-negotiable:** `SECURITY INVOKER` (not `DEFINER` — the caller is already the service-role admin client, which bypasses RLS on its own; `DEFINER` would run as the function owner regardless of caller and is unnecessary here), `REVOKE ALL ON FUNCTION upsert_best_score FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE ... TO service_role` only. Postgres functions are granted to `PUBLIC` by default — skipping this would turn a score-integrity fix into a score-*forging* endpoint reachable directly by any authenticated client, bypassing the replay verifier entirely. The still-live old constraint means the currently-deployed edge function keeps working unmodified through this phase.
   - **Phase 2 (edge function):** `submit-score/index.ts` calls the new RPC via `admin.rpc('upsert_best_score', {...})` instead of the current select+upsert. Deploy and verify it's live (e.g. a real submission + a `scores` row check) before Phase 3 — this repo's `submit-score` does not auto-redeploy from a `_shared`/function commit, so "deployed" must be confirmed, not assumed.
   - **Phase 3 (migration):** once Phase 2 is confirmed live, drop the old `(player_id, utc_date, difficulty)` constraint — safe now that nothing references it.
7. **Lightweight observability.** Emit `score_submit_attempt` and `score_submit_result` (outcome: success/terminal-rejection/retryable-failure, plus difficulty — never the move log) through the existing `onAnalyticsEvent` hook already wired into `GameCubit` (reused as-is, no new plumbing), so a recurrence of silent score loss is visible without needing a user report to notice.
8. No new user-facing error UI — consistent with the existing "the result screen never blocks" design; the finished board + move log are already durably persisted via `storage.saveSnapshot`, so nothing is lost locally across retries.
9. Add/update tests: `SubmitResult.reason` parsing; `GameSessionFactory`'s `SubmitResult`→`SubmitOutcome` mapping (including the unrecognized-reason default); `_submit` outcome branching and `submitStatus` transitions (`none→pending→settled` on success/terminal, stays `pending` on retryable failure, `pending` persisted before the network call so an offline-exit-then-later-online-relaunch retries successfully); `loadSubmitStatus`/`saveSubmitStatus` default to `none` for missing/legacy data (not `pending`); all three resume branches (`pending` retries unconditionally, `none`-but-terminal retries, `none`-and-non-terminal stays silent); resumed-`settled` seeds the in-memory guard so a subsequent `submitIfPending()` (e.g. Main Menu tap) makes no network call; a background resume-triggered retry that resolves *after* the player takes an ad continue does not clobber the freshly-continued snapshot (submit status and board snapshot are independently keyed); concurrent resume+submitIfPending calls coalesce into one full attempt (no double persistence/analytics, not just no double network call); `upsert_best_score` concurrent-submission behavior (keeps the higher score, respects season), its grants (only `service_role` can execute), and its `search_path` pinning (matches `0005`/`0006`/`0010`'s existing convention) at the SQL/Edge Function level; the phased migration doesn't break the old edge function mid-rollout (old constraint still satisfies the old `onConflict` target through Phase 1); a stale submission for a superseded (pre-continue) board is discarded rather than persisted once a newer generation exists, and the improved post-continue score still submits; `submitStatus` is wiped on account switch (excluded from `_installKeys`) so a previous account's stale write can't suppress the new account's same-day tier.

### Track B — Invite/share flow repair
10. **Facebook/OS-share text fix, with a predefined fallback if Facebook drops it.** Extend `ScoreSharer`'s interface (`lib/infrastructure/score_sharer.dart:14,29-41,44-50`) so `shareToFacebook` and `shareToSheet` both accept an optional `text`/caption parameter. Wire `lib/presentation/screens/score_share_screen.dart:370-371` to pass the already-existing, already-null-safe `_textSummary()` (`score_share_screen.dart:376-387`) through — it already degrades gracefully when `friendCode` is null, so no new null-handling is needed. Add the `EXTRA_TEXT` extra to the native Facebook intent in `android/app/src/main/kotlin/com/kidd/connect_merge/MainActivity.kt:106-111`. The OS-sheet fallback gets this for free once `ShareParams(text: ...)` is populated.
    - **Acceptance criterion beyond the seam test:** a passing unit test only proves the text argument reaches the platform channel/`share_plus` call — it does not prove Facebook's composer actually displays it (that app is known to sometimes ignore accompanying text on an image-type `ACTION_SEND`, and it can do so while the native intent still reports launch success, so `shareToSheet` never gets a chance to run as a fallback). Verify on a real device with Facebook installed.
    - **Predefined fallback if verification shows Facebook drops the caption:** the "Invite a friend" button's proof-of-working is text-only (no attached image) — it doesn't prove Facebook preserves text when an image is *also* attached, and that combination may get the caption dropped regardless of which Android API surface hands it to Facebook (native intent or OS share sheet). So the fallback ladder, decided by device-test outcome rather than left open at implementation time: first try routing through the OS share sheet with both image and text (`shareToSheet`, `ShareParams(text: ..., files: [...])`); if that *still* drops the caption specifically when Facebook is the selected target, drop the image for that path and share text-only (matching the already-proven Invite-button pattern) or fall back to an explicit "copy invite link" action — the caption/link being visible takes priority over the score-card image when the two conflict on Facebook specifically.
11. **Guest-eligible install-referrer redemption.** In `lib/infrastructure/redeem_coordinator.dart`'s `_isReady` gate (~line 277-279), drop the `_hasGoogleIdentity()` requirement for `RedeemSource.installReferrer` inputs (leave `RedeemSource.liveLink`'s gating untouched) so a fresh guest install auto-redeems and links friends without requiring sign-in first. Anonymous Supabase sessions already exist at this point (`auth.ensureSignedIn()` fires at boot, `main.dart:113`), so the redeem RPC has a valid `auth.uid()` regardless of Google-linking status. This is a constructor-level dependency wired from `main.dart:190` and referenced by existing `RedeemCoordinator` tests/harnesses — update the call site and the now-obsolete gating test(s) too, not just the internal check, so nothing is left as dead state or a stale test asserting the old behavior.
12. **No app-side link-format change needed.** `FriendsService.inviteHttpsLink()` already embeds the friend code as a URL path segment (`/invite/<code>`); the Play Install Referrer parameter needs to be appended by the *website's* redirect logic (see Out of scope), not generated by the app.
13. Add/update tests: `ScoreSharer` seam test asserting text is passed through; `RedeemCoordinator` test asserting an install-referrer-sourced code redeems without a linked Google identity, and that `liveLink`-sourced codes are unaffected.

## Key decisions & tradeoffs
- **Root-cause fix over point patch (Track A):** the originally-reported symptom already resolved itself via an unrelated DB wipe done in a different session today, but the underlying swallow-and-never-retry defect is unchanged and is the same bug class this codebase has shipped before (the challenge-mode check-constraint incident). Fixing it now, while it's cheap and in context, rather than treating today's wipe as the fix.
- **Retry via existing resume path, not a new persistent queue:** `LeaderboardService.submitRun`'s docstring promises "callers can queue + retry," which was never built. Rather than building a new offline queue/backoff system (mirroring `RedeemCoordinator`'s much heavier machinery), this plan reuses the snapshot-resume path already in `GameCubit.init()` as the retry trigger — bounded naturally by how often a player reopens a completed tier, no new subsystem. Bounded by UTC rollover, not unlimited (see Approach item 5) — the server structurally can't accept a backfilled prior day, so no amount of client persistence changes that.
- **Outcome-based retry, not throw-based (revised after review):** the initial design assumed a 422 always throws, which is false — `submitRun` returns `SubmitResult(valid: false, reason: ...)` normally for a server-side rejection (confirmed by the existing test suite). Retry eligibility is now keyed off the actual outcome (`reason == 'submit_failed'` and any unrecognized reason are transient/retryable; `reason == 'invalid_run'` is terminal-but-loudly-reported, since it's either tampering or a genuine engine-parity bug silently eating a legitimate score — the single most dangerous failure mode this codebase's own docs call out).
- **An app-owned `SubmitOutcome` type, not the raw infrastructure `SubmitResult` (revised after review):** the first draft had `GameCubit`'s callback return `SubmitResult` directly, which would force `game_cubit.dart` to import `leaderboard_service.dart` (and transitively `supabase_flutter`), breaking the plugin-free callback boundary every other `GameCubit` hook (`onCoinsEarned`, `onTierCompleted`) already respects. `GameSessionFactory` — already the documented infra/application bridge — does the mapping instead.
- **Persisted tri-state submit status as its own storage entry, not embedded in `GameSnapshot`, not a boolean, and not a re-derived terminal check (revised three times after review):** draft 1 gated resume-retry purely on recomputing "is this board terminal" from raw board state — that silently breaks the exact path most likely to have originally failed (`submitIfPending()` on an explicit main-menu exit has no terminal gate by design). Draft 2 fixed that with a boolean `submitAttempted` embedded in `GameSnapshot` (bumping `kSnapshotVersion`) — but a boolean can't distinguish "attempted and already settled" from "still needs retry" (re-submits every already-successful tier on every future resume), and embedding it in `GameSnapshot` meant a background retry finishing after the player takes an ad continue could overwrite the freshly-continued snapshot with the stale pre-continue board, and bumping `kSnapshotVersion` would discard every in-progress/completed game fleet-wide at deploy (`game_cubit.dart:250-252` has no fallback for a version mismatch). Draft 3: `none | pending | settled`, as its own `StorageService` entry decoupled from the board snapshot entirely (so it literally cannot race with `saveSnapshot` calls elsewhere), decoded with missing/legacy data defaulting to `none` — not `pending`, which would have force-finalized every legacy continue-eligible board on first post-deploy resume (draft 3 initially got this default wrong too; corrected in the same round once the consequence was traced through). Draft 4 (final): decoupling the storage key from the board snapshot fixed board-clobbering but not a subtler sibling — a stale in-flight retry for a *pre-continue* board can still resolve after the player continues to a *better* board under the same `(date, difficulty)` key, and without more, its late `settled` write would suppress the improved board's own submission. Closed with a generation counter: `_submit()` only applies/persists an outcome if the generation it captured at attempt-start still matches the current one at resolution; a superseded attempt's result is discarded, never written. Also account-scoped via the existing `wipeAccountData()`/`_installKeys` mechanism (the new key is simply not added to the survive-wipe allowlist) so a stale write from a previous account can't bleed into the next one.
- **Server-side atomic upsert added mid-review, not originally scoped — and season-scoped, and access-locked:** independent review found three compounding issues in what the first draft called "confirmed correct": (1) the existing read-then-upsert is a genuine lost-update race, worsened by this plan's second retry trigger; (2) the naive atomic-upsert fix would have used the *current* (season-less) unique constraint, reproducing a different pre-existing latent bug this session's own research already flagged; (3) a new privileged RPC needs an explicit `SECURITY INVOKER` + revoked-`PUBLIC`-grants contract or it becomes a client-reachable score-forging endpoint. All three closed together in one migration since they're the same piece of surface. A real scope increase over the original three symptoms, kept because leaving a known score-integrity race and a latent grant hole in place while adding a mechanism that makes the race more reachable would be irresponsible. Flagged here explicitly so it's visible at sign-off, not buried.
- **No differentiated retry cap for `invalid_run`:** it's marked terminal (not retried) rather than capped-and-retried, since the replay verifier is deterministic — retrying the identical move log against the identical server logic can never produce a different result.
- **Predefined Facebook-share fallback, not an open question deferred to implementation time:** if real-device verification shows Facebook's composer drops `EXTRA_TEXT` even when set, the plan already specifies the fallback (route through the OS share sheet instead of the Facebook-targeted native intent) rather than leaving that decision for whoever implements it to improvise.
- **Relaxing the Google-identity gate for install-referrer redemption** trades a mild anti-abuse guard for matching the actual product ask ("automatically applies the reference number and links the two as friends" on install, no sign-in mentioned). Live-link-sourced codes (`RedeemSource.liveLink`) keep whatever gating they already had — only the install-referrer path changes, including its call site and existing tests.
- **Facebook share fix is plumbing + a real-device check, not a guaranteed outcome:** passing `EXTRA_TEXT`/`text:` proves the app did its part; whether Facebook's composer actually surfaces it is platform behavior outside this repo's control, so the acceptance bar includes a manual on-device verification, not just a green test suite.
- **Website changes (hosting + Play Store referrer redirect) are explicitly out of scope for this repo/session** — that code lives in `connectmerge-site`, a separate repo the user will handle in its own session. This plan hands off an exact spec (below) instead of guessing at that codebase's structure. iOS Universal Links additionally need an Associated Domains entitlement wired into *this* repo's Xcode project (currently absent, per Info.plist's own comment) — hosting AASA on the website alone would not be sufficient even if that were in scope.

## Risks / open questions
- The `connectmerge-site` handoff spec (Out of scope, below) is unverified against that repo's actual structure since it wasn't explored this session — the user will need to adapt file paths/framework specifics there.
- Relaxing the install-referrer redemption gate slightly widens who can link as a "friend" without identity verification (an anonymous/guest account). Acceptable per the product ask, but worth a second look if this repo's friend system later gates anything sensitive on "friend" status.
- iOS has no Play Install Referrer equivalent; auto-apply-on-install for iOS installs (App Store) is not addressed by this plan and remains a known gap (Android was the confirmed-broken, tested platform).
- No user-facing indicator if a score submission keeps failing across multiple app-reopens before UTC rollover (e.g. a persistently expired/broken session) — it would retry silently on every resume until the window closes. Considered acceptable per the "off the critical path" design plus the new attempt/result analytics events (item 7); revisit if that telemetry shows this happening in practice.
- The `upsert_best_score` migration/edge-function change (item 6) requires a production deploy + verification step this session didn't originally scope for — treat it as its own careful commit, not bundled silently into the client-side fix.

## Out of scope
- Any change inside `connectmerge-site` (separate repo) — but here is the exact spec that repo needs, for the other session to implement:
  1. Host `https://www.connectmerge.app/.well-known/assetlinks.json` — standard Android App Links verification JSON, asserting `com.kidd.connect_merge`'s release-signing SHA-256 fingerprint, `relation: ["delegate_permission/common.handle_all_urls"]`.
  2. Host `https://www.connectmerge.app/.well-known/apple-app-site-association` — standard `applinks` JSON for the iOS bundle id/team id, for Universal Links. Note: insufficient by itself — the iOS app also needs an Associated Domains entitlement (see below), which is a change to *this* repo, not the website.
  3. On `https://www.connectmerge.app/invite/<code>`: if the visiting device doesn't open the app (i.e., the page actually renders, meaning App Links/Universal Links didn't intercept it), redirect Android visitors to `https://play.google.com/store/apps/details?id=com.kidd.connect_merge&referrer=code%3D<code>` (the `code=` key inside `referrer` must match exactly, since `InstallReferrerService.parseCode` in this repo reads it via `Uri.splitQueryString(referrer)['code']`) — and iOS visitors to the App Store listing (no referrer mechanism available there).
