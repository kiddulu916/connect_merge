# Plan: Fix "Long Chains Only" Challenge soft-lock
_Locked via grill — by Claude + kiddulu916_

## Goal
The daily Challenge rule `ChallengeRule.longChainsOnly` rejects any chain shorter than 3 tiles (`game_cubit.dart:277`), but nothing else in the engine knows that minimum exists. `GameEngine.hasMergeAvailable`/`evaluateStatus` only check whether *any* 2-tile mergeable pair exists, and `GameEngine.refill` only guarantees a 2-chain before it stops topping up the board. So once the board's only remaining mergeable adjacencies are 2-chains, the rule rejects every move the player tries, but the engine still reports `GameStatus.playing` forever — a soft-lock, not a real ending. It's byte-identical in the TS replay verifier (`engine.ts`), so this isn't platform drift, it's a shared spec hole. Fix it so (a) the engine is aware of each rule's minimum legal chain length everywhere that matters — initial board generation, post-move refill, and end-of-run status — so the run only ever truly deadlocks when no chain of the required length exists anywhere on the board, and (b) `longChainsOnly` gets a denser starting board so there's more material to work with before that can happen. This does **not** change board size, move budget, or make Challenge boards vary per-account — the daily deterministic board (same puzzle for every player) is working as designed; only the "no chains left" detection and starting density change.

## Approach
1. **Single-source the minimum chain length per rule.** Add `ChallengeRule.minChainLength` (Dart extension in `challenge_rule.dart`, mirrored as a lookup in `constants.ts`): defaults to **`2`** (the existing baseline — every current rule and difficulty already requires a 2-tile merge to count as "available," so this default is a no-op everywhere except the new case) and **`3`** for `longChainsOnly` only. Reject/assert values below 2 — a length-1 "chain" is a single tile, never a legal move. Replace the two independent `3` literals — `game_cubit.dart:277`'s reject-guard and `engine.ts:381`'s verifier guard — with reads of this property.
2. **Add a rule-aware chain-existence search.** On the Dart side, add it to `GameEngine` (no cycle: `DailySeeder` already imports `game_engine.dart`). On the TS side, put it in **`constants.ts`** alongside `canFollow`/`pairMergeable` — **not** `engine.ts` — because `engine.ts` imports `seeder.ts` already; putting the search in `engine.ts` and having `seeder.ts` call it would create an import cycle. `constants.ts` has zero imports (confirmed) and is already the shared leaf module both files depend on. Given a board and a `minChainLength`, the search determines whether a legal Connect-Merge chain of at least that length exists anywhere (DFS/BFS from each tile along `canFollow`-adjacent, unvisited neighbours, capped at `minChainLength` depth). Must agree with what `isValidChain`/`GameEngine.isValidChain` would accept for an equivalent path — it's the "does a legal move exist" complement to that validator. `GameEngine`'s functions are shared across every difficulty (confirmed grid sizes: Easy 8x8, Medium 7x7, Hard/Legendary/Challenge 6x6 — `difficulty.dart:6-10`), so the search must work generically up to 8x8, not just Challenge's 6x6; still cheap for an exhaustive per-cell search at that size.
3. **Thread `minChainLength` through every call site that decides "is this board/run playable":**
   - `GameEngine.refill` — its internal guarantee condition (currently `!hasMergeAvailable(board)`) becomes "no chain of `minChainLength` exists," so it keeps dropping tiles (as room and the drop stream allow) until a legal chain of the required length is present, not just any 2-chain. `game_cubit.dart`'s call passes `_activeRule?.minChainLength ?? 2`.
   - `GameEngine.evaluateStatus` — same swap, so `GameStatus.deadlocked` is only set once no chain of the required length remains.
   - `DailySeeder.generate`'s re-roll loop (`daily_seeder.dart:150`) — currently re-rolls only until a 2-chain exists, so a `longChainsOnly` board could theoretically start already unable to satisfy its own rule. Re-roll against the rule's `minChainLength` instead (new parameter alongside `startingFillOverride`/`wallCountOverride`/`movesOverride`). Mirror in `supabase/functions/_shared/seeder.ts`.
   - **`GameCubit._finishRun`'s terminal check (`game_cubit.dart:404-406`)** — the third OR-clause (`!GameEngine.hasMergeAvailable(board)`, used to decide "no ad-continue is actually possible, submit now") is the same stale rule-unaware predicate. Left as-is, it would stay `false` whenever a bare 2-chain exists even though no legal 3-chain does, deferring submission and leaving `canOfferAd` free to offer a continue that both replays uselessly (no legal move exists under the rule) and, per the next point, would poison the whole run's server verification anyway. Swap it for the same rule-aware search — **and** (added after Codex round 2) make `terminal` unconditionally `true` whenever `_difficulty == Difficulty.challenge`, full stop. Reasoning: once `canOfferAd` (next bullet) is hard-`false` for all Challenge runs, an out-of-moves Challenge board that still has a legal chain would otherwise never satisfy any of the three original OR-clauses (not deadlocked, `adContinuesUsed` stays 0 forever since no continue is ever granted, and a legal chain existing makes the rule-aware predicate `false` too) — leaving the run stuck in `GameOverShowScore` with `_submit` never called. Challenge has no continue path at all, so any non-`playing` status for Challenge is terminal by construction.
   - **`GameCubit.canOfferAd` (`game_cubit.dart:574-580`)** — currently ignores difficulty entirely, so it can return `true` for a Challenge run (any rule) that's out of moves with a bare 2-chain sitting on the board. But `verifyRunChallenge` (`engine.ts:391-393`) rejects **any** `ContinueEvent` for Challenge mode outright, regardless of rule (`"Challenge mode has no ad-continues; treat any continue as illegal"`). So today, tapping the ad-continue button on a Challenge board that's out of moves doesn't extend play — it silently dooms that day's submission to server rejection (`invalid_run`), which surfaces nowhere client-side (see the existing "GameCubit swallows submit result" gap). This is a **pre-existing bug affecting every Challenge rule**, not something this plan introduces — but leaving it unfixed while fixing the terminal-check above would make the inconsistency *worse specifically for `longChainsOnly`* (immediate submission fires, then a still-offered continue button either double-fires submission attempts or bakes in a doomed one). Fix: gate `canOfferAd` to `false` whenever `s.difficulty == Difficulty.challenge`, matching the server's blanket rejection exactly. Small, targeted, and directly in the code path this plan already touches — flagged here explicitly since it's broader than "Long Chains Only" alone.
4. **Give `longChainsOnly` a denser starting board.** In `game_cubit.dart`'s per-rule fill switch (`:219-223`), add a `longChainsOnly => kChallengeDenseFill` branch (reuse the existing constant, no new one) instead of falling through to the default 8.
5. **Bump `kLeaderboardSeason`** in both `lib/domain/constants.dart` and `supabase/functions/_shared/constants.ts` per the repo's standing rule for any gameplay/deadlock/seeded-generation change, so old and new Challenge scores never mix on a leaderboard.
6. **Bump `kSnapshotVersion`** (`lib/domain/constants.dart:140`) — corrected after Codex round 2. `GameCubit.init()` recomputes `_targetFill` fresh from the current rule-fill switch on *every* init, even when a persisted snapshot's board is reused as-is (`game_cubit.dart:213-237` runs before the snapshot check at `:239`). Today that's harmless because `longChainsOnly` has always used the same fill (8) as the default. Once it gets its own denser branch (step 4), a player with a same-day in-progress snapshot saved *before* this ships would resume on their old 8-fill board but have `_targetFill` recomputed to 14 — `GameEngine.refill` would then top the old board up toward a target it was never generated for, producing a played history that's internally inconsistent with either the old or new generation logic (and which the server, which always regenerates fresh from `seeder.generate()`, could never validate either way). Bumping the version forces any in-flight snapshot to discard and restart fresh under the new logic, exactly matching its own doc comment's purpose (`storage_service.dart:16-18`: "discarded on load... starts the day fresh under current rules"). Note this does **not** fix server-side replay mismatches during a rollout window (the server doesn't read this constant at all) — that's a separate, accepted risk, next point.
7. **Deploy ordering (accepted risk, not eliminated by any code change):** this changes what `DailySeeder.generate()`/`seeder.ts` produce for `longChainsOnly` boards. Per the existing "Edge function deploy after engine changes" pattern in this repo, the `submit-score` Edge Function redeploy should ship at the same time as (or just before) the app build reaches players, to minimize — not eliminate — the window where a client is generating boards under one ruleset while the server verifies under the other. Because app-store rollout is inherently asynchronous (phased rollout, review delays, users who don't auto-update), some in-flight Challenge runs during that window can still fail submission; this is the same category of risk every prior gameplay-rule change in this repo has carried (mitigated by `kLeaderboardSeason`, not eliminated), not something unique to this fix. A durable fix (e.g. a minimum-client-version gate) would be a separate, larger initiative — out of scope here unless requested.
8. **Write the required design doc + task plan** under `docs/superpowers/specs/` and `docs/superpowers/plans/` per this repo's planning workflow (`CLAUDE.md`) before implementation begins — this touches the dual-engine invariant (deadlock detection, seeded generation) that the workflow exists to protect.
9. **Tests:** `game_engine_test.dart` cases for the chain-search itself — a board where only a 2-chain exists (search for length 3 returns false), a board with a real 3-chain along each direction (search returns true, matches `isValidChain`), a case at the tier cap (an ascend-chain that would exceed `kMaxTier` doesn't count), and a default-`minChainLength`(2) regression case confirming standard/non-`longChainsOnly` behavior is byte-identical to today's `hasMergeAvailable`; a `refill` test asserting it keeps dropping past a 2-chain-satisfied state when `minChainLength: 3` and room/drops remain, and stops if the board fills up first; a seeder test asserting the re-roll loop won't hand back a `longChainsOnly` board that's already short of a 3-chain; `game_cubit_challenge_test.dart` cases driving a `longChainsOnly` run into a real dead end (asserts `GameOverShowScore`, not a stuck `GamePlaying`) and asserting `canOfferAd` is `false` throughout any Challenge run regardless of rule; TS mirrors of all of the above (chain-search, refill, seeder re-roll) in `engine.test.ts`/`seeder.test.ts`. Existing Challenge tests should be checked for vacuous assertions (early returns that skip the check under some conditions) rather than assumed sufficient. **Added after Codex round 2:** a deterministic multi-date sweep (e.g. a bot that always plays the first legal chain the search function finds, across ~200+ sample dates) asserting a full-board deadlock never occurs, or occurs at a rate low enough to sanity-check the "denser start + rule-aware refill" tuning actually works as intended rather than assuming it from reasoning alone.

## Key decisions & tradeoffs
- **"Same three chains on all accounts" is expected, not a bug.** Confirmed with the user: the daily deterministic board (identical puzzle for every player, replay-verified server-side) is the core fairness model and is out of scope to change. The complaint is specifically that the *same* soft-lock happens to everyone, not that it's shared.
- **`minChainLength` defaults to 2, not 1** (corrected after review) — a default of 1 would make the "no legal chain" search vacuously false for every board with any tile at all, silently breaking deadlock detection for every non-`longChainsOnly` case. Defaulting to 2 makes the new rule-aware path a strict no-op everywhere except `longChainsOnly`.
- **Rule-aware fix threads through five call sites, not one** (refill, evaluateStatus, seeder re-roll, `_finishRun`'s terminal check, `canOfferAd`) — fixing only `evaluateStatus` would end the game sooner but not give players more chances (that's `refill`'s job), and fixing only the deadlock path while leaving `_finishRun`/`canOfferAd` on the old predicate would leave a live/dead inconsistency between "the run already submitted" and "the UI still offers a continue."
- **`canOfferAd`'s Challenge-wide fix is in scope, not just `longChainsOnly`,** because the server already rejects all Challenge continues unconditionally — matching that exactly is simpler and more correct than trying to special-case only `longChainsOnly`'s no-3-chain state, and leaving the broader bug in place would specifically undermine this plan's own fix.
- **`minChainLength` is single-sourced on `ChallengeRule`** rather than leaving `3` as independent literals in `game_cubit.dart` and `engine.ts` — it's now read by four engine/cubit call sites plus the existing reject-guard, so a shared source avoids a fifth place for the numbers to drift apart.
- **TS chain-search lives in `constants.ts`, not `engine.ts`** — `engine.ts` already imports `seeder.ts`; putting the new search there and having the seeder's re-roll call it back would create an import cycle. `constants.ts` is a zero-import leaf both files already share (`canFollow`/`pairMergeable` already live there for the same reason).
- **Starting density reuses `kChallengeDenseFill` (14)** rather than a new constant — matches the existing per-rule override pattern (`denseStart`/`sparseStart`/`wallMaze`/`budgetCut` all reuse a single constant each).
- **No change to board size (stays 6x6) or move budget (stays 30).** `DailySeeder.dropTierAt` draws from an unbounded PRNG stream (confirmed identical in both `daily_seeder.dart` and `seeder.ts` — `refillBoard`/`refill` call it directly, not a fixed-length array), so a more aggressive refill loop can pull as many additional tiles as it needs without a schedule-exhaustion risk — bounded only by empty cells on the board.
- **`kSnapshotVersion` bump is in scope after all (reversed after Codex round 2)** — not for the reason first proposed ("so the server can replay it"; the server never reads this client-local constant) but because `_targetFill` is recomputed fresh from the rule-fill switch on every `init()` independent of whether a persisted snapshot's board is reused as-is. Once `longChainsOnly` gets its own fill branch, an in-flight same-day snapshot saved before this ships would resume on an 8-fill board while `_targetFill` silently becomes 14, producing an internally-inconsistent play history. Bumping the version forces a clean restart, matching the constant's own stated purpose.
- **Rejected: a new ruleset/ContentVersion system for replay verification.** The suggestion to "version the replay rules and stamp submissions into the matching season until old clients are retired" is a materially bigger feature than this bug fix warrants — the repo's existing `kLeaderboardSeason` bump plus deploy-ordering discipline (point 7) is the established mitigation for this repo's whole dual-engine architecture, applied to every prior gameplay-rule change, not just this one. Building new infrastructure for a one-rule bug fix is out of proportion; a minimum-client-version gate is a reasonable idea but a separate initiative.
- **Rejected: reworking `goldenDropIndices()`'s `kMaxDrops`-bounded precompute.** A `longChainsOnly` run that needs many extra drops chasing a 3-chain could reach a drop index beyond the precomputed golden-eligible set (0..38), so very late drops in a long Challenge run simply never get the cosmetic golden flag. Confirmed cosmetic-only — golden tiles never affect score or replay on either side. Documenting this as an accepted, known ceiling (code comment) is proportionate; rearchitecting the precompute into an on-demand check is unnecessary engineering for a non-functional edge case.
- **Rejected (for this plan): structured rejection telemetry for replay-verification failures.** A real observability gap (this repo's `submit-score` already collapses all verifier rejections into one `invalid_run`, and the "GameCubit swallows submit result" gap means players never see it), but it's a separate cross-cutting improvement, not something this specific bug fix requires to be correct. Worth a follow-up, not bundled here.

## Risks / open questions
- **Full-board deadlock is still possible in principle** — if all cells fill and still no 3-chain exists, `refill` has nowhere left to drop and the rule-aware `evaluateStatus` will (correctly) report `deadlocked`. This is a legitimate end state, not a bug — the multi-date sweep test (approach step 9) measures how often it actually happens rather than assuming it's rare from reasoning alone.
- **`engine.ts`/`seeder.ts` mirror correctness** — the TS chain-existence search and re-roll condition must match the Dart implementation byte-for-byte per the repo's dual-engine invariant; `golden_vectors.json` is the tripwire if they drift.
- **Golden vector fixtures WILL shift** for `longChainsOnly` — starting fill 8→14 changes the initial board outright, and the rule-aware refill/re-roll changes its trajectory. Regenerate with `UPDATE_GOLDENS`, review the diff is only the expected effect (not an unrelated regression), and re-run both the Flutter and Deno suites before committing.
- **Deploy-window submission failures are a known, accepted risk category in this repo** (see approach step 7) — reduced by deploying client and edge function together, not eliminated by any code change; app-store rollout is asynchronous so some window always exists.
- **`canOfferAd`'s Challenge-wide fix is a behavior change beyond `longChainsOnly`** — every Challenge rule stops offering ad continues (previously offered but silently doomed to server rejection). Worth confirming there's no UI copy/analytics elsewhere that assumes Challenge continues are reachable, since this plan only touches the cubit logic.

## Out of scope
- Making Challenge boards vary per player/account (breaks the deterministic-fairness architecture the whole game is built on).
- Changing board size, move budget, or any other `ChallengeRule`'s behavior.
- A UI/copy change to explain the rule to players (not requested).
- A general replay-verification rejection-telemetry system (see Rejected list above) — worth raising separately.
- Reworking `goldenDropIndices()` beyond documenting its known ceiling.
