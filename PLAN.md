# Plan: Diagonal chain adjacency + sum-based merge value
_Locked via grill — by Claude + kiddulu916_

## Goal
Connect Merge's only "move" is dragging a path across adjacent tiles, which then collapses (`GameEngine.collapseChain`); there is no directional-shift mechanic. This plan (1) extends the chain-drag adjacency rule from 4-directional (orthogonal) to 8-directional (orthogonal + diagonal), and (2) replaces the current "ascend-chain" merge-value rule — where a collapsed chain's endpoint always becomes `peakTier + 1` regardless of chain length — with a sum-based rule: the merged tile's value is the largest power of two ≤ the sum of every tile's value in the dragged chain, with any remainder simply discarded. The existing same-tier-or-ascend-by-1 step rule, the existing base-score formula (`2^tier × length-multiplier + ascendBonus`, inlined in `collapseChain`) and `ascendBonus`, and the dual-engine (Dart + hand-mirrored TS) architecture are all preserved; only the geometry of what counts as an adjacent step and the arithmetic of what a collapse produces change. This is a full replacement of the ascend-chain rule (no dual-mode), applies to every difficulty and challenge mode, and additionally removes the `kMaxTier` cap on merging itself (tiles can now grow past 2048) while keeping `kMaxTier` as an unchanged reference constant for the cosmetic/economy systems (achievements, near-miss detection, share-grid, loot tuning) that are already walled off from score/move-log per `CLAUDE.md`.

## Approach
1. **Diagonal adjacency.** Extend the geometry check used by `isValidChain` (`lib/domain/engine/game_engine.dart:204`) from 4-directional to 8-directional — a step is legal between any of the 8 neighboring cells. **Rename `areOrthogonallyAdjacent` to `areAdjacent`** (Dart) and its TS equivalent, in both definitions and every call site — the old name would now be a false description of what the function actually checks. No corner-cutting restriction: a diagonal step is valid purely based on whether the destination cell holds a live tile and passes the tier rule, regardless of what's in the two flanking orthogonal cells (even if both are walls).
2. **Deadlock/refill correctness — and every other place `kMaxTier` gates legality, not just `isValidChain`.** There are two genuinely independent scan implementations per language, each with its own embedded geometry list and terminal cap check — confirmed by reading both, not four shared call sites as first assumed:
   - **Dart:** `hasMergeAvailable` (`game_engine.dart:99`) + private `_pairMergeable` (`:121`) — the length-2 fast path, hardcodes "east and south neighbours only" and `higher < kMaxTier`. Separately, `_searchChain` (`:149-151`) — the DFS used for `minLength > 2` — has its **own** hardcoded 4-directional neighbor list (`col±1`, `row±1`) and its **own** independent terminal check `tier < kMaxTier`, entirely unconnected to `_pairMergeable`.
   - **TS:** `hasAnyMergeablePair` (`constants.ts:172`) + `pairMergeable` (`:100`) mirror the Dart pair-scan exactly. Separately, `searchChain` (`:193`) mirrors `_searchChain` — same independent geometry + cap check, not routed through `pairMergeable`.
   - Plus `BoardWidget._canExtend` (`board_widget.dart:55`) on the UI side.
   All **five** call sites (2 Dart + 2 TS + 1 UI) must be updated together: geometry to 8-directional, `kMaxTier` legality check dropped. Leaving any one on the old rule would let the game declare "no moves available" (or block a UI drag step, or miss a `longChainsOnly`-style long-chain deadlock check) for a merge that `collapseChain` would actually have allowed.
3. **`DailySeeder`/board generation is in scope, not out of scope.** `DailySeeder.generate()`'s re-roll loop (`lib/domain/engine/daily_seeder.dart:102`, mirrored in `supabase/functions/_shared/seeder.ts`) accepts or re-rolls a board using `GameEngine.hasChainOfLength`/`hasMergeAvailable` — the same predicate being changed in step 2. Changing its adjacency/cap semantics changes which boards the re-roll loop accepts and how many PRNG draws it takes to get there, which changes the generated board itself for a nonzero share of dates (confirmed: 35 of 1,825 committed board-vector cases change under an 8-neighbor simulation). This must be tracked as a seeder-level change, not incidental fallout.
4. **Integer floor-log2 helper (the highest-risk piece).** Add a `mergedTierFromSum(int sum)` helper computing `floor(log2(sum))` via integer-only arithmetic — **not** floating-point `log()`, which can round incorrectly right at exact power-of-two boundaries (e.g. computing `log2(8.0)` as `2.9999999998` and flooring to 2 instead of 3). Dart may use `int.bitLength`-based arithmetic (Dart's 64-bit `int` has no truncation hazard at the proven ceiling); TS must NOT use `Math.clz32`/leading-zero-count — see the corrected technique in step 7 below. Both implementations must be behaviorally identical (same output for every input), even though their internal technique differs by language; this is the single most likely spot for silent Dart/TS drift and needs dedicated boundary-case unit tests in both.
5. **Rewire `collapseChain` directly — the standalone `comboScore()` helper is not actually in its call path, corrected from an earlier draft.** Read `collapseChain` itself (`game_engine.dart:242-271`): it does **not** call the standalone `comboScore()` helper at all — it inlines the same formula directly (`score: s.score + (1 << (mergedTier + 1)) * fn(path.length) + ascendTotal`, line 267), where `mergedTier = endTile.tier` (the pre-merge peak tier) and `fn = comboMultiplierFn ?? comboMultiplier` (line 264) — `comboMultiplierFn` is exactly how `comboRushMultiplier` overrides the default for the Combo Rush challenge rule. An earlier draft of this plan instructed calling `comboScore(resultTier - 1, chainLength)` from the caller — **that would silently bypass `fn`/`comboMultiplierFn` and break Combo Rush**, since `comboScore()` only ever uses the default `comboMultiplier`, never the override. Correct fix, entirely inside `collapseChain`: replace `mergedTier = endTile.tier` / `newTier = mergedTier + 1` with `resultTier = mergedTierFromSum(sum of every tile's value in the path)`; place `Tile(id: endTile.id, tier: resultTier)` (not `mergedTier + 1`); change the score line's exponent from `(1 << (mergedTier + 1))` to `(1 << resultTier)`, keeping `* fn(path.length) + ascendTotal` byte-identical so the Combo Rush override keeps working unmodified. Add an explicit regression test pinning a concrete numeric example under **both** the default multiplier and `comboRushMultiplier` (e.g. four tier-1 tiles summing to tier 3 must score `(1 << 3) * comboMultiplier(4) + 0`, and separately confirm the Combo Rush-scoped version scores `(1 << 3) * comboRushMultiplier(4) + 0`). **Delete the standalone `comboScore()` helper and its TS mirror (`engine.ts:99`), rather than leave it as a misleading survivor.** Confirmed by repo-wide search: it has zero production call sites in either language (Dart: only its own definition in `game_engine.dart`; TS: `export`ed from `engine.ts` but referenced only from `engine.test.ts`) — once `collapseChain` stops routing through it, keeping it around would describe a formula that no longer represents what a real collapse computes, actively misleading future readers. Its dedicated unit tests (`game_engine_test.dart`'s `comboScore` group; `engine.test.ts:410-416`'s `Deno.test("comboScore: ...")`) are deleted with it; the many other test assertions across both files that currently call `comboScore(tier, n)` as a shorthand for "expected score" (e.g. `engine.test.ts:279,484,498,507`) are rewritten to compute the expected value directly (`(1 << resultTier) * multiplier + ascendTotal`, matching `collapseChain`'s real formula) or via a small test-local helper, not the deleted production function. `ascendBonus` is unaffected — still keyed off tier deltas between consecutive *original* path entries.
6. **Validation timing stays at release, not live.** `BoardWidget._canExtend` (and `isValidChain`) keep validating only geometry (now 8-directional) + the same-tier-or-+1 step rule while the player is dragging. The sum-is-a-power-of-two computation happens once, at collapse. A structurally valid chain (adjacency + tier rule satisfied) is now *always* collapsible — floor-rounding means there's no separate "sum invalid" rejection path, so no new no-op/failure case is introduced.
7. **Numeric safety for uncapped tiers — required, not optional. The ceiling is now derived and verified, not guessed.** Two independent overflow risks, both a direct consequence of removing the merge cap: (a) TypeScript's `<<` operator is a **32-bit signed** bitwise op (`engine.ts:100,134` both use `1 << (mergedTier + 1)`) — unsafe once tiers grow large, diverging from Dart's native `int` (fixed 64-bit signed on this app's compile target — corrected from an earlier draft's wrong "arbitrary precision" claim) and breaking replay verification exactly where it matters most. (b) `scores.score` is an `int` (32-bit) column; a large cumulative day score can exceed Postgres's `int4` range.
   - **Derived ceiling: tier 17, verified against real constants (two prior drafts' assumptions were wrong and are corrected here).** `kCellCount`/`kGridSize` in `constants.dart` are *not* the true per-difficulty board size — `Difficulty.easy` (`lib/domain/models/difficulty.dart:6`) has `gridSize: 8` → 64 cells, the largest of any difficulty, confirmed by direct read. With `wallCountFor(easy) == 2` (`constants.dart:155`), a single chain is bounded by 62 non-wall cells. `kMaxDrops` is *not* a true daily drop ceiling either — `daily_seeder.dart:190`'s own comment confirms the drop-tier stream is "decoupled from board placement so refills can be unbounded" (a single monster-chain collapse can refill far more than one cell). The real bound: total moves per day ≤ 39 (`kMovesPerDay` 30 + `kMaxAdContinuesPerDay`×`kAdMoveReward` = 3×3 = 9); each move can refill at most 61 cells (62 non-wall cells minus the 1 surviving endpoint); each refilled drop is worth at most 64 (`dropCap` saturates at tier 6); initial board mass is at most `40 × 4 = 160` (Easy's `startingFill`, tiles capped at `dropCap(0) = 2` → value 4). Total value mass ever introduced in a day ≤ `39 × 61 × 64 + 160 = 152,416`, and since a collapse's sum can never exceed the total mass currently on the board (floor-rounding only ever *reduces* mass, drops are the only source of new mass), no single merged tile can exceed `floor(log2(152416)) = 17`. **Pin `17` as a named constant in both engines with this derivation in its doc comment**, and add a test asserting the mass invariant (not an attempt to enumerate every legal move sequence). **This is a physical invariant of real seeded gameplay, not a new runtime legality/rejection check — do not wire it into `isValidChain` or `collapseChain` as a cap.** Doing so would directly contradict step 6 (every structurally valid chain is always collapsible): a directly-constructed test `BoardState` (not produced by real seeded generation) can freely exceed 152,416 mass without that being a bug, since the invariant only holds for boards `DailySeeder` actually produces under real move/drop budgets. Its only uses are (a) sizing numeric types (`bigint` vs `int`, this step), (b) choosing a floor-log2 technique that's provably correct across the real range (next bullet), and (c) a debug-assertion/test invariant on seeded-generation output specifically — never a move-validity condition a player-facing action can fail.
   - Fix (a): replace `1 << n` with double-based exponentiation (`2 ** n`) in every TS power computation touching tier/value — exact and safe far beyond tier 17.
   - Fix (b): migrate `scores.score` to `bigint` (see step 7a for full RPC-surface fallout). `scores.highest_tier` stays `int` — tier ≤ 17 fits trivially. A full day's *cumulative* score (summed across up to 39 moves, each scaled by `comboMultiplier` for chains up to 62 tiles long) can plausibly reach into the low billions, comfortably exceeding `int4`'s ~2.1 billion ceiling but nowhere near `bigint`'s ~9.2×10^18 or JS's 2^53 safe-integer limit — confirming `bigint` is both necessary and comfortably sufficient.
   - **`mergedTierFromSum` in TS must NOT use `Math.clz32`, even though the proven ceiling (17) is well under its 2^31 safety threshold — corrected after review.** The function needs to stay correct for *any* caller, not only real seeded gameplay: a directly-constructed test `BoardState` is explicitly allowed to exceed the 152,416 mass bound without that being a bug (see the invariant note above), and `Math.clz32` would silently produce wrong results for such an input via its `ToUint32` coercion — an unacceptable footgun in a helper that's supposed to be a general-purpose, always-correct arithmetic primitive. Use a simple integer-division loop instead (`while (2 ** (exp + 1) <= n) exp++`, or equivalent) — correct across the full JS-safe-integer range regardless of caller, and no more complex than the bit-trick alternative.
   - 7a. **RPC-surface fallout of the `bigint` migration — five functions (corrected count), each recreated from its *current* (latest-migration) definition, not an earlier one.**
     1. `upsert_best_score` (`supabase/migrations/0014_atomic_score_upsert.sql`) — already exists, already live (`p_score int`/`score int`, `security invoker`, `search_path = public`, revoked from `public`/`anon`/`authenticated`, granted only to `service_role`). Postgres doesn't allow `create or replace` to change a parameter type, so the new migration must **drop and recreate** it with `p_score bigint`/`score bigint`, re-asserting the *exact same* security contract explicitly (grants do not survive a drop).
     2. `leaderboard()` — current definition is `0010_leaderboard_read_rpcs.sql`'s bounded `security definer` version with a `p_season` filter, **not** `0001`'s original (which `0010` superseded). Returns `score int`; recreate from `0010`'s body with `bigint`, preserving every clause.
     3. `friends_leaderboard()` (`0013_friends_leaderboard_player_id.sql:13`) — returns `score int`; recreate from its current, `player_id`-inclusive body with `bigint`.
     4. `leaderboard_period()` (`0010_leaderboard_read_rpcs.sql:55`) — already declares `total bigint`, computed via `sum()` over the now-`bigint` `score` column; Postgres's `sum(bigint)` returns `numeric`, which won't satisfy an already-`bigint`-declared return column, so add `sum(s.score)::bigint` explicitly.
     5. `friends_leaderboard_period()` (`0010_leaderboard_read_rpcs.sql:121`) — same `sum(s.score)::bigint` cast fix as #4.
     Recreating any of these from the wrong (superseded) migration's definition would silently regress authorization or response shape — always diff against the *latest* migration that touched each function, not the one that first created it. `my_daily_ranks`/`my_period_ranks` (`0010_leaderboard_read_rpcs.sql:~206,209`) return `rank`/`difficulty`, not `score`, directly — expected unaffected, but verify by reading their bodies rather than assuming, since both order by `score` internally.
   - 7b. **The existing SQL smoke suite (`supabase/tests/leaderboard_smoke.sql`) hardcodes the old signature and will break.** Line 317's `has_function_privilege('service_role', 'public.upsert_best_score(uuid,date,text,integer,integer,integer)', 'EXECUTE')` check embeds the literal old parameter-type signature string — it must be updated to the new `bigint` signature, alongside every other assertion in that file touching `upsert_best_score`/`leaderboard`/`leaderboard_period`/`friends_leaderboard`/`friends_leaderboard_period` (lines ~255-325 and any other call sites). Add a new assertion submitting a score above `2,147,483,647` (the old `int4` ceiling) to prove the migration actually fixed the overflow, not just changed a type name. Run this suite after `supabase db reset` as part of verification (step 21).
8. **Bump `kSnapshotVersion`.** `GameCubit.init()`'s resume branch (`lib/application/game_cubit.dart:254-257`) only checks `snap.version == kSnapshotVersion`, discarding any mismatch outright (`constants.dart:138-145`'s own doc comment: bumped "when a difficulty's per-rule generation inputs... change in a way that could leave an in-progress snapshot's board inconsistent," with prior precedent "for the Long Chains Only starting-density change"). This plan's change — both board generation (step 3) and collapse arithmetic (step 5) — is exactly the scenario that constant exists for. Bump it decisively rather than deferring the decision: every in-progress snapshot is discarded and regenerated fresh on next load, which is the established, low-risk, already-documented mechanism for this exact class of change in this codebase (unlike a data-*shape* change, no partial-preservation logic is warranted here — a discarded in-progress board simply regenerates, same as any other daily reset).
9. **Mirror byte-for-byte into `supabase/functions/_shared/engine.ts`/`constants.ts`/`seeder.ts`** per the dual-engine invariant, including doc comments stating the parity requirement, exactly as today's `canFollow`/`collapseChain`/`refillBoard` already do.
10. **Bump `kLeaderboardSeason`** in both `lib/domain/constants.dart` and `supabase/functions/_shared/constants.ts` so old (ascend-chain) and new (sum-based) scores never mix on a leaderboard.
   - 10a. **Season must be explicitly validated, not assumed enforced by replay divergence alone — and the rejection must stay externally indistinguishable from `invalid_run`, not become a new client-visible reason.** The client already sends `'season': kLeaderboardSeason` in the submit-score request body (`leaderboard_service.dart:104`), but `validate_request.ts` never extracts it and `index.ts` always stamps the server's own current `kLeaderboardSeason` when writing (`constants.ts`'s own comment: "the server uses its OWN constant when writing — it never trusts a client-supplied season"). For most multi-move runs, an old client's move log will fail replay anyway (see step 11) since board state diverges from the very first collapse under the new sum-based arithmetic, causing later moves' `isValidChain` checks against server-recomputed tile values to fail — but this is an *accidental* side effect of replay determinism, not a guaranteed defense: a short/coincidental old-rule run could still replay cleanly end-to-end and silently land in the new season with a server-recomputed (not old-client-displayed) score. Add an explicit check in `validateSubmitRequest`: extract `season` from the payload, and on a missing or non-matching value, return the **existing `invalid_run` reason externally** (not a new reason string) — `GameSessionFactory._submitRun` (`game_session_factory.dart:70`) maps only `reason == 'invalid_run'` to `SubmitOutcome.terminalRejection`; anything else falls through to `retryableFailure`, and a stale client's season can never become current without an app update, so any other externally-visible reason would make it retry forever on every resume. Internally (server-side logging only, via the same mechanism as step 20a), tag this rejection distinctly as `stale_season` so it's diagnosable without ever surfacing a client-parseable difference from an ordinary replay failure. This is strictly additive defense-in-depth using data already sent by every client build; requires no new client-side plumbing.
11. **Rollout ordering across client/server deploy skew — accepted tradeoff, not solved, and not actually bounded for every client.** Mobile clients can't be force-upgraded (app store review lag, and some users never update at all), so there is a window — for a non-trivial long tail of installs, an *unbounded* one — where an old-rule client's move log is submitted to the new-rule server. With step 10a's explicit season check, this is now a *deterministic* rejection (externally still `invalid_run`, internally logged as `stale_season` per step 20a) rather than one that depended on replay happening to diverge — a stale client's build-time `kLeaderboardSeason` constant will never match the server's post-bump value, so every stale submission is caught up front, before replay even runs, and the client's existing terminal-rejection handling (`GameSessionFactory._submitRun`) applies correctly without needing to learn a new reason string. On review this was pushed back on as understating the problem by calling it "bounded"; the pushback is fair for the never-updating tail (that install is permanently locked out of submitting, not merely delayed), but **building new infrastructure to solve it (dual-verifier routing by rule version, or enforced minimum client version) is rejected as out of scope**: this codebase's own established practice for every prior gameplay-rule change is a `kLeaderboardSeason` bump with no dual-verifier or version-gating mechanism (per `CLAUDE.md`), and no such mechanism exists anywhere in this codebase today. Adding one here would be new scope the user never asked for, applied inconsistently (this would be the only rule change with it). Documented honestly as an accepted, *not fully bounded*, cross-cutting limitation of how this codebase already ships every gameplay-rule change — not newly introduced by this plan.

## Key decisions & tradeoffs
- **Diagonal adjacency is additive (8-directional), not a replacement**, and applies to the existing chain-drag gesture — there is no new directional-shift mechanic being introduced; "move" in this codebase means "drag a chain."
- **Full replacement of the ascend-chain rule everywhere** (all difficulties, all challenge modes) rather than a second selectable mode — avoids indefinitely maintaining two merge rules across both engines.
- **Mixed-value chains remain allowed, but only non-decreasing** (same tier or ascend by exactly 1 per step) — identical ordering constraint to today's `canFollow`, just now checked across 8-directional geometry instead of 4.
- **Merged value = floor-power-of-two of the chain's value sum; excess is discarded, not carried or rejected.** Confirmed against a concrete edge case: a basic 2-tile ascend merge (a 2 into a 4) sums to 6, floors to a merged tile worth 4 — net zero board-value growth even though the player still scores points and frees a slot. Accepted as a natural consequence of the rule; uniform same-value chains (2+2+2+2, 4+4+4+4) never lose value since count × value is always an exact power of two when the count itself is.
- **Sum validity is checked only at collapse (release), not live during the drag.** Simplest implementation; a structurally valid drag is always collapsible, so no new rejection UX is needed.
- **No corner-cutting restriction on diagonal steps** — a diagonal step is legal purely from destination-cell + tier-rule validity.
- **Merging is fully uncapped past `kMaxTier`/2048 up to tier 17**, a derived-and-verified physical ceiling (Approach step 7) distinct from the removed gameplay cap — the true maximum any legal day's play can reach given real move/board/drop constants, not an arbitrary technical buffer. `kMaxTier` itself is otherwise left completely alone as the reference constant for cosmetic/economy systems (achievements, near-miss, share-grid, loot tuning) — those stay pinned to "2048 is the milestone" unmodified, since they're already walled off from score/move-log per `CLAUDE.md`'s determinism model.
- **Scoring formula (`2^resultTier × length-multiplier + ascendBonus`) is unchanged in shape**, computed inline inside `collapseChain` exactly as today, with only the exponent's source changing (sum-derived `resultTier` instead of `peakTier + 1`). An earlier draft of this plan proposed routing through the standalone `comboScore()` helper — rejected on review, since that helper hardcodes the default multiplier and bypasses `comboMultiplierFn`, which is exactly how Combo Rush overrides scoring. `comboScore()` itself has no production callers (confirmed by repo-wide search, both Dart and its TS mirror — test-only) and is now deleted rather than left as a misleading helper that no longer represents what `collapseChain` actually computes (see Approach step 5).
- **`DailySeeder`/board generation is explicitly in scope**, not walled off — both adjacency (step 2/3) and the dropped `kMaxTier` legality check change what boards the seeder's re-roll loop accepts, confirmed to change ~2% of committed board-vector fixtures.
- **A derived tier-17 production bound is required for numeric type sizing and test assertions (not runtime enforcement)**, since removing the merge cap entirely exposes two independent overflow bugs (JS 32-bit bitwise shift; Postgres `int` columns) that exist in the codebase today but were previously masked by `kMaxTier=11` keeping tiers small. This bound is never wired into `isValidChain`/`collapseChain` as a legality check — see Approach step 7's explicit prohibition.

## Risks / open questions
- The integer floor-log2 computation is the highest-risk piece of this whole change for Dart/TS drift — must be integer-only arithmetic in both languages, never floating-point `log()`, and needs boundary-case tests specifically at exact powers of two. Resolved: TS uses the integer-division loop from Approach step 7 (not `Math.clz32`, which is unsafe for out-of-bound test-constructed inputs — see step 7's derivation).
- Rollout ordering (Approach step 11) is an accepted tradeoff explicitly *not* fully bounded for clients that never update — flagged honestly rather than understated, but not solved with new infrastructure (rejected as scope this codebase's own prior rule changes never needed; confirmed on review as consistent with existing repo precedent).
- The fate of the vestigial `GameEngine.canMerge` predicate specifically (not `_pairMergeable`, which is live) is left to implementation-time judgment.
- Per review, the `BoardWidget` per-cell highlight likely needs no rendering change for diagonal paths (no connector painter exists to update), but this is only confirmed once the new widget test (step 17) is written and passing, not assumed in advance.
- Server-side rejection logging (step 20/20a) is scoped to season/difficulty/rejection-stage only — an app-build dimension was initially proposed but dropped since the client's submission payload (`leaderboard_service.dart:77-82`) has no build/version field to source it from; plumbing one in is a separate, out-of-scope effort if wanted later.

## Out of scope
- New difficulty tiers or per-difficulty variation of the merge rule.
- Redesigning achievement/near-miss/loot systems around an open-ended tier scale — `kMaxTier` stays as their fixed reference point.
- Combo Rush / Long Chains Only challenge-specific rules beyond staying compatible with the new merge computation — they continue layering on top unchanged (`comboRushMultiplier`, `minChainLength`).
- Solving client/server rollout skew with new infrastructure (e.g. dual-verifier support, minimum-client-version enforcement) — named as an accepted, *not fully bounded* tradeoff (step 11), not built here.
- Plumbing a client build/version identifier into submission payloads for server-side observability — logging is scoped to what's already sent (season) plus rejection stage/difficulty.
