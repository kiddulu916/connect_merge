# Plan: Extract `LocalOwner.canPush` — single-source the sync push-eligibility predicate
_Locked via grill — by Claude + kiddulu916_

## Goal
The push-eligibility rule "may this install push its profile for `uid`?" — `owner.uid == uid && restoreComplete && !recoveryRequired && claimed` — is written inline, identically, in two places in `ProfileSyncService` (`arm()` and `_pushOnce()`), reading four `LocalOwner` fields at each site. Extract it to a single `LocalOwner.canPush(String uid)` so the rule lives once, with the fields it reads and the doc that explains them (locality), and the two sync sites ask for an answer instead of reassembling four fields. Behavior-preserving; client-only (no TS mirror).

## Approach
1. Add `bool canPush(String uid)` to `LocalOwner` (`lib/infrastructure/storage_service.dart:34`), returning `this.uid == uid && restoreComplete && !recoveryRequired && claimed`. Document it, folding in the existing `claimed`-field rationale (why arming requires a real server claim, not a bare uid match). **The doc comment MUST state (Codex R1 #2) that this is the SYNC push-eligibility predicate only — it requires a server `claimed` and is NOT the storage write-guard (which omits `claimed` to allow offline/unclaimed writes) nor the recovery-UI gate; those deferred follow-ups must not reuse `canPush`.**
2. TDD (RED first): add `test/infrastructure/local_owner_test.dart` with a truth table — a fully-eligible owner returns `true`; each of {uid mismatch, `restoreComplete == false`, `recoveryRequired == true`, `claimed == false`} returns `false`.
3. **Close the `_pushOnce()` coverage hole (Codex R1 #1) BEFORE the swap.** Existing tests pin `arm()` eligibility (`profile_sync_service_test.dart:333`) but none pins the `_pushOnce()` owner-ineligible branch. Add an integration test to `profile_sync_service_test.dart` with this EXACT recipe (Codex R2 #1 rejected the naive one — `rebindOwner` sets `_syncedRevision = _localRevision`, clearing dirty, so an unforced `pushNow()` returns `clean` and never reaches `_pushOnce()`):

7. Commit (single commit: method + tests + two call-site swaps).

## Key decisions & tradeoffs
- **Predicate home = `LocalOwner` method, not `StorageService` method, and not a private helper in `ProfileSyncService`.** `LocalOwner` owns all four fields and their doc; a `StorageService.canOwnerPush` wrapper would add a method to the very interface this candidate wants to slim, and would not remove `storage.owner` exposure anyway (`bootstrap()`, `main.dart`, `account_flow_controller` all still read `owner`). **Codex R1 #2 suggested a private `_ownerCanPush` inside `ProfileSyncService` instead — REJECTED on locality + the locked decision, not on single-sourcing (Codex R2 correctly noted a private helper WOULD still single-source the fields): putting the predicate on `LocalOwner` keeps it with the data it reads and the `claimed` doc that explains it, whereas a private sync helper separates rule from data. The user locked "method on `LocalOwner`" in the grill.** The "invites misuse by the write-guard" risk Codex raised is real and is mitigated by the mandatory doc comment in Approach step 1, not by hiding the method. Tradeoff: each site keeps a `owner != null && owner.canPush(uid)` null check rather than one storage call — accepted; the null-owner case is a real caller concern and the interface stays unchanged.
- **`canPush(String uid)` takes a NON-null uid.** Both callers already guard `uid == null` before the field checks, so `canPush` stays a pure predicate over a real uid and never encodes the "no signed-in user" state. `String?` (letting callers drop their null-uid guard) rejected to keep the predicate pure and the diff minimal.
- **Scope = `canPush` only.** The same four fields also drive (a) the storage **write-guard** (`!restoreComplete || recoveryRequired` → `StorageWriteBlockException`, duplicated in `hive_storage_service.dart:124-131` and `InMemoryStorageService` `storage_service.dart:275-281`) and (b) the **`main.dart` recovery-UI gate** (`:106-122`). These are DIFFERENT predicates (write-guard omits `claimed`; UI gate is presentation) with wider blast radius. Deferred as **prioritized follow-ups**, deliberately not folded in, to keep this change tightly reviewable and behavior-preserving.
- **Behavior-preserving refactor guarded by existing + one new integration test.** (Wording corrected per Codex R1 #4.) Only the **four-field owner-eligibility subpredicate** is identical at each site — `!canPush(uid)` equals the inline `uid != owner.uid || !restoreComplete || recoveryRequired || !claimed` by De Morgan (Codex verified this). Each caller's OTHER guards and branch bodies are preserved verbatim: `arm()` keeps `_armed || _superseded || uid == null`, `_pushOnce()` keeps its distinct `uid == null → return failed` (no log/disarm) path and its `_onLog + _disarm + return failed` block. The new `canPush` unit test pins the truth table; the new `_pushOnce` integration test (Approach step 3) plus `arm requires a complete matching owner` and `storage_ownership_test` pin that both sites' behavior is unchanged.

## Risks / open questions
- **Short-circuit / ordering equivalence.** The four-field owner-eligibility subpredicate is believed identical at both sites (Codex verified the De Morgan equivalence; wording corrected per Codex R2 #4 — this is about the subpredicate, not a whole-site "byte-identical boolean"). Mitigation: keep each caller's existing null/sync-state guards exactly and replace ONLY the four owner-field sub-expression; the existing sync tests are the net. Note `arm()` currently evaluates `localOwner.uid != uid` etc. only after `localOwner == null` short-circuits — `owner != null && owner.canPush(uid)` preserves that ordering.
- **Over-extraction guard.** `canPush` replaces only the CONDITION. `_pushOnce()`'s failure branch (`_onLog` + `_disarm()` + `return ProfilePushOutcome.failed`) and `arm()`'s bare `return` stay per-site — they are not part of the predicate.
- **`claimed` default.** `LocalOwner.claimed` defaults to `false` (older records re-claim). `canPush` requiring `claimed` preserves today's behavior exactly; no migration.
- **Pre-existing in-flight race — NOTED, out of scope (Codex R1 #3).** `_pushOnce()` checks eligibility, awaits the `push_profile` RPC, then `markPushed()`s whichever owner exists afterward; `claimAndRestore()` (via `account_flow_controller.reloadProfile`) `_disarm()`s but does not drain an already-in-flight push, so an accepted old push could advance a newly-restored owner's revision. This bug **predates this refactor and this change neither introduces nor fixes it** — a behavior-preserving predicate extraction must not silently alter drain/concurrency semantics. Tracked as a SEPARATE follow-up (drain-before-claim + a completer-based race test), not folded in here. (Note: `pauseAndDrain waits for an in-flight old-account push` at `profile_sync_service_test.dart:258` already drains on the pause path; the gap is specifically the claim/restore path.)
- **Observability — NOTED, out of scope (Codex R1 #5).** `_pushOnce()` logs every rejection reason as the single string `profile push blocked: local owner mismatch`. This is pre-existing imprecision; changing the string is an observable behavior change (and risks a log-asserting test), so it is NOT changed here. A per-reason diagnostic (tie it to the write-guard's `StorageWriteBlockReason`-style enum) is a follow-up alongside the deferred write-guard work.
